## Models
- `Finding` exactly as in architecture.md §8. Additional rules:
  - `id` = `f"{rule_id}:{device_ids}:{subject}"`, deterministic
  - `source="deterministic"`
- `Recommendation(setting_id, device_id, current_value, recommended_value, rationale, manual_action: str)`.
  HACA v1 never applies changes, so every recommendation is a manual action. It is attached to the
  finding as `recommendation: Recommendation | None`.
- Validators that make invalid findings unrepresentable:
  - `evidence` non-empty
  - `classification == CONFIRMED_CONFLICT` requires every evidence `tier in {isapi, browser}`, and
    `basis == technical` or every `orp_refs` value explicit (not unspecified/undecided)
  - `needs_decision=True` requires `classification in {INFO}`

  In **simulation**, the evidence tier is `simulation`. The engine therefore downgrades CONFIRMED to
  `POTENTIAL_CONFLICT` and sets `simulated_confirmed=True`, so reports can show "would be CONFIRMED on a
  live device". This keeps the invariant intact.

## Rule framework
```python
class Rule(Protocol):
    id: str; title: str; category: str; basis: Literal["technical", "requirement"]
    default_severity: Severity
    requires: tuple[str, ...]        # DeviceViews fields needed
    requires_orp: tuple[str, ...]    # ORP dotted paths
    def evaluate(self, ctx: RuleContext) -> list[Finding]: ...
```
- `RuleContext`: collection views per device, correlation, ORP, the coverage index, and a helper
  `evidence(device_id, endpoint_id, xpath, value)`.
- Engine behaviour:
  - when any required view is missing or inaccessible for the subject, the engine emits one
    `INSUFFICIENT_DATA` finding (severity `info`) naming the missing data, instead of calling `evaluate`
  - it catches rule exceptions and turns them into an `INSUFFICIENT_DATA` finding with
    `rule_error=True`, logged
- ORP helper `orp.value(path)` returns the explicit value or `None` for unspecified/undecided.
  `orp.is_explicit(path)` is also provided.

## Correlator
- Maps NVR `ProxyChannelView.ip` to configured camera devices by exact IP.
- Produces:
  - `channel_of[device_id] -> nvr_channel`
  - `unknown_channels` (proxy IP not in config)
  - `unattached_devices` (configured camera without an NVR channel)

## Acceptance criteria
1. Against `scenario-clean` with the seed ORP, the run contains zero CONFIRMED/POTENTIAL findings. Only
   INFO and `needs_decision` entries remain, for `hik_connect` and `ptz_mode`.
2. Against `scenario-conflicts` with the seed ORP, every planted conflict from T2.01 §3 is detected by
   the expected rule. In simulation it is downgraded to POTENTIAL with `simulated_confirmed=True`.
3. Same scenario with an empty ORP: no CONFIRMED and no `simulated_confirmed` for requirement rules.
   Only technical rules may be `simulated_confirmed`.
4. Model validators reject:
   - CONFIRMED without evidence
   - CONFIRMED based on an undecided ORP value
   - CONFIRMED with simulation tier
5. Missing data produces INSUFFICIENT_DATA, never a conflict. Test by removing `record.tracks` from a
   profile.
6. Findings are deterministic: same input → same IDs and order. Sort by severity, then rule ID, then
   device ID.
